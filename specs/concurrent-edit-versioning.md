# Concurrent Edit Versioning

## Description

I want to introduce versioning to file content so that concurrent edits from multiple clients can be detected and intelligently merged rather than silently overwriting each other.

### uniqueId Utility

I want a new Go function `uniqueId(length int) string` that generates a random alphanumeric string using 62 possible characters (a-z, A-Z, 0-9).

### FileId Migration

FileId should change from a UUID to a 12-character string generated by `uniqueId(12)`. Remove the `github.com/google/uuid` dependency. Collisions are assumed never to happen.

### VersionId

Each file should have a `VersionId` column in the `files` SQLite table (`TEXT NOT NULL`). No migration is needed — the test database will be deleted. A VersionId is a 5-character alphanumeric string generated by `uniqueId(5)`. Uniqueness is assumed per-file (not globally). A new VersionId is generated whenever file content is written — via the API or via the file watcher.

### Content Payloads Include VersionId

Every place file content is returned or broadcast must include the VersionId:
- `GET /api/files/:id` response body gains a `versionId` field
- `{ type: "content" }` WebSocket broadcast gains a `versionId` field

### Client Behavior

The frontend stores a `fileVersions` map (fileId → versionId) in the store, populated whenever content is loaded or received via WebSocket. The `writeFile` function in `api.js` gains a `uniqueId(5)` generator (JS equivalent: random alphanumeric). Before sending a `PATCH`, the client reads `currentVersionId` from the store and generates a `newVersionId`. It optimistically sets `store.fileVersions[fileId] = newVersionId` immediately. For rapid successive writes, `currentVersionId` is always the most recently *sent* `newVersionId` — not the last server-confirmed one.

The PATCH request body becomes `{ content, currentVersionId, newVersionId }`.

### Backend Write Handling (Happy Path)

When the backend receives a PATCH, it compares the supplied `currentVersionId` against the `VersionId` in the `files` table.

If they match, the client was up to date:
1. Update `files` table with new content and `newVersionId`
2. Write to disk
3. Store an entry in RecentFileVersions (see below)
4. Broadcast `{ type: "content", fileId, content, versionId: newVersionId }` to all other subscribed clients (excluding the sender)
5. Return 204

### RecentFileVersions

An in-memory structure (keyed by fileId + versionId) storing `{ fileId, versionId, content, timestamp }`. Populated on every successful content write — clean writes, conflict-resolved merges, and watcher updates. A background goroutine runs every minute and purges entries older than 5 seconds. This short window is sufficient because it only needs to cover in-flight requests from fast-typing clients.

### Backend Write Handling (Conflict Path)

If `currentVersionId` does not match the DB's `VersionId`, the client was working from a stale version. The backend looks up `currentVersionId` in RecentFileVersions for that file.

**No matching RecentFileVersion:** Return a 409 response with body `{ content: <current DB content>, versionId: <current DB versionId> }`. Make no changes.

**Matching RecentFileVersion found:** Attempt a 3-way merge using `github.com/sergi/go-diff/diffmatchpatch`:
- `clientOldContent` = the RecentFileVersion's content (what the client thought was current)
- `clientNewContent` = the content supplied in the request
- `currentContent` = the DB's current content

Compute the diff from `clientOldContent` → `clientNewContent`, then apply it to `currentContent`. This succeeds when different regions of the file were edited.

**Merge succeeded:** Generate a new VersionId for the resolved content. Update the DB, write to disk, store in RecentFileVersions, broadcast `{ type: "content", ... }` to ALL clients (including the sender). Return 204.

**Merge failed (conflicting edits to same region):** Return a 409 with body `{ content: <current DB content>, versionId: <current DB versionId> }`. Make no changes.

### Client Conflict Handling

When the client receives a 409, it shows a toast notification informing the user their change was rejected due to a conflict, then updates `store.fileContents[fileId]` and `store.fileVersions[fileId]` from the error response body. The Editor reactively picks up the content change.

### File Watcher

When the watcher detects an external disk change, it generates a new VersionId, updates the DB (content + VersionId), stores in RecentFileVersions, and broadcasts to all subscribed clients. There is no `currentVersionId` check — external disk changes are authoritative.
