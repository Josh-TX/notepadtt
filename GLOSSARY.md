# Glossary

## FileId

12-character alphanumeric string assigned to each file on creation, generated by `uniqueId(12)`. Replaces the prior UUID scheme. All frontend and backend logic is FileId-centric — edits, WebSocket messages, tab state, and LastOpened tracking all reference FileId. FileId persists through renames; when a file is renamed the Path column in SQLite updates but FileId stays the same. Collisions are assumed never to happen given the 62^12 keyspace.

## VersionId

5-character alphanumeric string stored in the `files` table alongside content, generated by `uniqueId(5)`. Assigned when a file is created, updated on every content write (WS edit or watcher). Included in all content-related payloads: `GET /api/files/:id` response, the `{ type: "edit" }` WebSocket message (as both `currentVersionId` and `newVersionId`), `{ type: "content" }` broadcasts, and `{ type: "editConflict" }` messages. The client sends its last-known versionId as `currentVersionId` and a freshly generated one as `newVersionId`; it optimistically treats `newVersionId` as current and keeps sending further chained edits off it until a WS message says otherwise. The server compares `currentVersionId` against the DB to detect concurrent edits. When a conflict is resolved via relocation, the server commits the merge under a freshly minted versionId rather than the client's own `newVersionId` — that id is never written to the DB, but is still recorded in RecentFileVersions against the naive (non-merged) content, so the client's next chained edit can still resolve its base. Uniqueness is assumed per-file (not globally).

## RecentFileVersions

In-memory store on the backend holding recent content snapshots. Each entry contains `fileId`, `path`, `versionId`, `content`, and `addedAt`. Populated on every successful content write — clean writes, conflict-resolved merges, and watcher-triggered updates — keyed by the DB-committed versionId. Additionally, when a conflict is resolved via relocation rather than rejected, an extra entry is stored under the client's own submitted `newVersionId` holding the naive (non-merged) content — i.e. what the client's local editor actually has — even though that versionId itself is never committed to the DB. This lets that client's next chained edit still find a snapshot to diff against. Used during conflict resolution: when an incoming edit's `currentVersionId` doesn't match the DB's latest versionId, the server looks up `currentVersionId` here to find the snapshot to line-diff against the latest content, remapping the edit's position before applying it. Entries expire after 5 seconds, but are no longer purged by their own standalone ticker — purging now happens as the final step of each FileVersioning process run. RecentFileVersions is also the exclusive content source for FileVersion rows: the FileVersioning process reads entries straight out of this list (never re-reading `files.Content`) to decide what to persist. Every entry is equally eligible for persisting, including the naive non-committed entry — no special-casing excludes it.

## FileVersion

A row in the `FileVersions` table: a persisted historical content snapshot for a file, with columns FileId, Path, Content, VersionId, Date, and Term. Always sourced from a RecentFileVersions entry — FileId/Path/Content/VersionId/Date are copied verbatim (Date = that entry's `addedAt`), never re-read from the `files` table. Rows are immutable: inserted once by the FileVersioning process, never updated, and eventually hard-deleted once past the TTL for their Term (see Term). Deleting the underlying file does not cascade-delete its FileVersion rows — they age out naturally via TTL (a future "restore deleted file" feature will rely on this). Indexed by (FileId, Term, Date) and (Term, Date) to support the FileVersioning process's per-FileId date lookups and TTL sweep. Backed by a `fileversions_fts` FTS5 table (trigram tokenizer, Path+Content indexed, content_rowid=Id) kept in sync via `AFTER INSERT`/`BEFORE DELETE` SQL triggers — safe to use triggers here since FileVersion rows never get updated. This FTS table is unused for now; it exists ahead of a future full-text-search-over-history feature. FileVersion rows are exposed to the frontend read-only via `GET /api/files/{id}/versions` (used by HistoryModal), which returns all rows for a FileId merged with on-the-fly preview entries: RecentFileVersions entries for that FileId are run through the same cascading Term-eligibility rules the FileVersioning process uses, without persisting anything, so a HistoryModal user can see a version that hasn't been written to the FileVersions table yet but would be on the process's next run. The endpoint always returns the full list for a file — no pagination.

## Term

The cumulative 1-4 retention-tier int on a FileVersion. Term=1 means short-term only; 2 means short+med; 3 adds long; 4 adds very-long. Determined at insert time by the FileVersioning process via cascading MinDelay checks (see FileVersioning process), and later used to pick which TTL constant governs that row's eventual deletion (the TTL of the row's own highest tier). Governed by 8 hardcoded Go constants (no user-configurable settings yet):

- ShortTermTTL=10m, ShortTermMinDelay=40s
- MedTermTTL=120m, MedTermMinDelay=8m
- LongTermTTL=7d, LongTermMinDelay=18h
- VeryLongTermTTL=60d, VeryLongTermMinDelay=5d

Duration strings are parsed case-insensitively with units s/m/h/d, with an optional space between the number and unit (e.g. "8m", "8 M").

## FileVersioning process

Background job that replaces the old standalone RecentFileVersions-cleanup ticker; runs once a minute. Each run: (1) deletes FileVersion rows past the TTL for their Term; (2) collects the distinct FileIds currently in RecentFileVersions; (3) runs one grouped query to get, per FileId, the most recent Date for each cumulative term threshold (`MAX(Date) WHERE Term>=N` for N=1..4); (4) for each FileId, walks its RecentFileVersions entries oldest-to-newest, skipping any entry less than ShortTermMinDelay past the running Term>=1 date, otherwise cascading the N=2,3,4 MinDelay checks against the running Term>=N dates (stopping at the first failure) to pick the row's final Term, inserting a FileVersion row, and updating the running per-term date trackers — so a single run can persist more than one FileVersion row for the same FileId; (5) purges RecentFileVersions entries older than 5 seconds; (6) deletes FileTrash rows whose DateDeleted is older than TrashTTL (30m). Because Date is written verbatim from the source RecentFileVersions entry and the per-term lookup is re-queried fresh each run, an entry that survives un-purged into a later run is safely re-evaluated as ineligible rather than double-persisted.

## FileTrash

A row in the `FileTrash` table: FileId, Path, Content, DateDeleted, Size (plus an autoincrement Id PK, following the same pattern as `files`/`FileVersions`). Rows are created in three scenarios, all routing through the same internal soft-delete logic: (1) UI-triggered deletion via the TabBar/FileTree context-menu "Delete" action — no confirmation prompt, the file is removed from disk, its `files` row is hard-deleted, and a FileTrash row is inserted with Content/Size copied from the file's last-known DB content; (2) fsnotify-detected on-disk removal (watcher.go); (3) startup-scan detecting a tracked file missing from disk. Folder deletion (recursive, still gated by a native `confirm()`) also inserts one FileTrash row per contained file, but never shows a toast — not even an informational one. Watcher/startup-detected deletions are likewise silent (no toast), matching today's watcher behavior; those files are recoverable only via TrashModal.

UI single-file deletion shows a toast (see Toast) with an UNDO action that calls the restore API. Restore (`POST` to a per-fileId restore route, shared by both the toast's UNDO and TrashModal's restore button) re-creates the `files` row reusing the original FileId — so the file's FileVersion history reconnects immediately — and writes Content back to disk at the original Path, recreating any missing parent folders (`MkdirAll`) if the original folder was itself deleted in the meantime. If a file already exists at that Path, the restore reuses the exact same `NextDuplicateName` logic as the Duplicate feature (so it can land on "(2)", not "(1)" — consistent with Duplicate's numbering, not a separate convention). The restored file is appended at `Max(OrderNum)+1` in its destination folder, the same rule as any newly created file. The write itself goes through the normal internal content-write path, so it mints a fresh VersionId and a RecentFileVersions entry exactly like any other edit — no special-casing in the versioning pipeline. The FileTrash row is deleted immediately on a successful restore. After restore, the client opens the restored file in the editor and navigates CurrentFolder/breadcrumbs to its folder — identical behavior whether restore was triggered via the toast or via TrashModal. If a restore fails (e.g. the row already expired or was emptied from another client), no special recovery UX is provided; the lack of redirection makes the failure self-evident.

TrashModal additionally offers a per-item "Delete Forever" button (right-pane footer, no confirmation prompt — low stakes, single item) and a sidebar-footer "Empty Trash" action that deletes every FileTrash row, gated by a native `confirm()`. Rows also expire automatically once TrashTTL (30m) has elapsed since DateDeleted, swept by the FileVersioning process's per-minute tick alongside its other TTL work.

## TrashModal

Overlay opened via the Trash row in Sidebar — styled like the Search row, positioned immediately below it. Header just says "Trash". Unlike HistoryModal, the sidebar is always visible, even on mobile — no collapse behavior at all. Fetches the trash list fresh every time the modal opens (a list endpoint returning, per row: fileId, path, lineCount, length, dateDeleted — no content), pre-sorted most-recently-deleted first; no live refresh while the modal stays open, matching HistoryModal's fetch-once-per-open convention. A small filter input at the sidebar's top-left does case-insensitive substring matching against path, operating purely on the already-fetched in-memory list (no refetch, no server round-trip). Each sidebar item shows the original path (left-ellipsis truncated, so the filename stays visible) on line 1, and DateDeleted + Size on line 2 — Size formatted with binary units (1024 B = 1 KB, 1024 KB = 1 MB), same convention as a typical file manager.

Clicking a sidebar item fetches that trashed file's content on demand (a separate route from the list) and displays it read-only in the right pane, styled like HistoryModal's content viewer. The right-pane footer has a text "Restore" button (calls the same restore API as the delete-toast's UNDO — see FileTrash) and a "Delete Forever" button (permanently removes that FileTrash row, no confirmation). The sidebar footer has an "Empty Trash" button that deletes every FileTrash row at once, gated by a native `confirm()` prompt. On successful restore, TrashModal closes and the restored file opens in the main editor, with CurrentFolder navigating to match (same as clicking a Search result).

## CurrentFolder

The folder currently being viewed, reflected in the navbar breadcrumb trail. Scopes the TabBar (only files in CurrentFolder are shown as tabs) and determines where new files are created. Navigating via the sidebar "open" button or clicking a file in the FileTree updates CurrentFolder. Defaults to root on first load.

## TabBar

Horizontal scrollable strip between the Navbar and Editor. Shows one tab per text file in CurrentFolder — not just opened files, all files. Full width, no buttons; sidebar toggle and "+" live in the Navbar. Tabs show filename only (not full path). Right-clicking a tab shows a context menu: Delete, Rename, Duplicate, Download, History. History opens HistoryModal for that tab's file, regardless of whether the right-clicked tab is the active one. The active tab is highlighted with a 2px solid #0078D4 top border and #1f1f1f background. When CurrentFolder has no text files, shows centered muted text: "no text files in this folder".

## Search

Workspace-wide full-text search across all files' path and content, powered by FTS5 with trigram tokenizer. Triggered via the Search Modal. Query terms are split on whitespace and OR-joined; results ranked by bm25 with path weighted 3× over content; top 10 returned. Each result includes the full relative path, a 4-line SearchSnippet around the best-matching line, and the startLineNumber. Clicking a result navigates to the file's folder, opens the tab, and scrolls the editor to the matching line.

## SearchModal

Overlay UI for running a Search. Contains an autofocused text input and a scrollable results list. On mobile: full-screen with a header row (input fills remaining width, close button on right). On desktop: large centered modal with a max-width. Input changes immediately clear results; a subtle loading indicator appears during the 400ms debounce + API call. Results show the full relative path and SearchSnippet per file. Empty query shows "Type to search…" placeholder. Last query and results persist in memory across modal open/close — results do not auto-refresh on filesystem changes.

## SearchSnippet

4-line excerpt of file content returned per Search result. Backend finds the line with the most case-insensitive substring matches against the search terms, then takes 1 line before + that line + 2 lines after (fewer if at file boundaries). Displayed read-only with actual file line numbers on the left, dark background styled like the Editor, and matching terms highlighted in yellow/orange.

## Sidebar

Collapsible left-side panel containing a Search section above the FileTree. On desktop (≥768px): slides in from left, ~400px wide, pushes the entire layout (navbar, tabbar, editor, footer) to the right. On mobile (<768px): fixed-position overlay, slides in from left over the content without pushing anything. Contains a collapse button at the top, a clickable Search row (magnifying glass icon + "Search" text, full-width, slightly larger than a FileTree row) that opens the SearchModal, a Trash row immediately below it (same styling/sizing, trash-can icon + "Trash" text) that opens TrashModal, and the FileTree below both.

## Navbar

Topmost bar. Left edge: sidebar toggle button (static icon, not state-dependent). Then "NTT" label (not a link), followed by breadcrumb trail to CurrentFolder. Right edge: "+" button to create a new file in CurrentFolder. On desktop, all breadcrumbs except the rightmost are clickable links. On mobile, no breadcrumbs are clickable. Shifts right when Sidebar opens on desktop.

## Editor

CodeMirror 5 instance occupying the full space between TabBar and Footer. Uses `viewportMargin: Infinity` so the browser's native find (Ctrl+F) works across the entire document. Features: word wrap (toggleable, default on) and line numbers. No syntax highlighting, no themes beyond the custom dark colors. Background color #1f1f1f.

## Footer

Bottom bar pinned to the screen edge. Left side: undo button, redo button, word-wrap toggle (shows a checkmark unicode char when enabled), History button. Both undo and redo are placeholder/non-functional in the initial implementation. The History button opens HistoryModal for the active file; it's always clickable, even when the file has zero history (HistoryModal shows an empty state in that case). Right side: displays "length: X lines: Y" where length is byte count of current file content.

## HistoryModal

Overlay opened via the History option in the TabBar/FileTree context menus, or the History button in Footer. Fetches `GET /api/files/{id}/versions` fresh on every open — never cached across opens. Layout: a sidebar listing versions on the left, a read-only content viewer on the right.

Sidebar: a "Current Snapshot" entry is always pinned at top (shows the label "Current Snapshot" instead of a timestamp, plus its length/lines), followed by a flat list of past versions newest-first by Date — no grouping or tier badges. Past versions mix persisted FileVersion rows with on-the-fly preview entries (RecentFileVersions entries for that file that would become eligible on the FileVersioning process's next run); previews get only a very subtle visual distinction from persisted rows. Each non-Current entry shows an absolute, locale-formatted date/time, byte length (same raw byte count convention as Footer), and line count.

Current Snapshot's content source depends on whether the file is the currently active/open tab: if so, it's a frozen copy of the editor's live content taken at modal-open time (not kept in sync with further WS content updates while the modal stays open); otherwise it's fetched via `GET /api/files/{id}` with `cid` omitted, which skips both UpdateLastOpened and Subscription so peeking at another file's history doesn't mark it as opened.

Content viewer: read-only, styled like the Editor/SearchSnippet (dark background, monospace font, line numbers starting at 1 for that version's content), but lines never wrap — long lines scroll horizontally, and the pane scrolls vertically for the full file. Its markup/styling is independent from SearchSnippet's (not a shared component).

Mobile: modal is full-screen (100vw/100vh, no border-radius), matching SearchModal's mobile mode. Sidebar is collapsible via a button fixed at the modal's top-left; collapsing animates sidebar width down to 0 over 150ms, letting the content pane fill the width; selecting a version while the sidebar is expanded auto-collapses it afterward. Desktop: sidebar is a fixed 300px, not resizable and not collapsible. On both mobile and desktop the sidebar is capped at 60% of modal width, so the cap overrides the 300px default on narrow viewports.

View-only in this version of the feature — no restore/revert action.

## FileTree

Has two meanings depending on context:
1. The visual component inside the Sidebar — a hierarchical browser of all files and folders from the server root; only text files are listed (same scope as TabBar). Folders are expandable/collapsible (click to toggle). Clicking a file navigates to its folder (updates CurrentFolder) and opens its tab; on mobile also closes the Sidebar. Each folder row has a small "open" button that navigates to that folder; on mobile also closes the Sidebar. Right-clicking a folder shows: New File, New Folder, Delete Folder (recursive, with confirmation), Rename Folder. Right-clicking a file shows: Rename, Delete, Duplicate, Download, History (opens HistoryModal for that file). Folders listed before files; folders sorted alphabetically, files sorted by OrderNum. Hidden files (dotfiles) are shown.
2. The data structure returned by the backend representing all nested files and folders, sent over HTTP on initial load and re-broadcast over WebSocket on any filesystem change. Each file node includes an `orderNum` field.

## OrderNum

0-based integer column in the SQLite `files` table. Determines display order of files within a folder — both in the TabBar and in the sidebar FileTree. Folders are unaffected; they remain alphabetically sorted. Rules: new files (via POST or fsnotify discovery) get Max(OrderNum)+1 within their folder; on fresh server start with no DB, files are assigned OrderNums alphabetically. Duplicating a file inserts the copy at original's OrderNum+1, incrementing all higher-OrderNum files in that folder. Deleting a file triggers recompaction (remaining files re-sequenced 0,1,2…). Users can reorder tabs on desktop via HTML5 drag-and-drop; `PUT /api/files/:id/order` with `{ targetIndex }` reassigns all OrderNums in the folder and broadcasts the updated FileTree.

## cid

UUID assigned by the server to each WebSocket connection on connect. Sent as the first WS message: `{ type: "init", cid: "<uuid>" }`. The client stores it and passes it as a `?cid=...` query param on REST calls (e.g. `GET /api/files/:id?cid=...`). The server uses it to associate HTTP requests with the correct WS connection, enabling subscription tracking. Stored in memory only — cleared on client disconnect or server restart.

## Subscription

Server-side record of which file a given cid currently has open. Established as a side-effect of `GET /api/files/:id?cid=...` — that call both returns file content and registers the subscription. One subscription per cid at a time; replaced whenever the client fetches a different file (tab switch). On WS reconnect the client gets a new cid and re-fetches the active file, re-establishing the subscription. The server uses subscriptions to target `{ type: "content" }` broadcasts — only the client subscribed to the edited file receives the update (excluding the sender). Stored in memory only — all subscriptions are cleared on server restart.
